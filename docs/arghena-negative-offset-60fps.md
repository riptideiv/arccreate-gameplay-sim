# Arghena 负音频起点失败与 60 fps 导出

失败演奏：`20261107-052014-bd2439`。修复后演奏：`20261107-052526-611446`。谱面 Arghena Future 11，范围 **0–160.797 s**，主速度 **3 m/s**、待机 **1 m/s**、抬指 **12 mm**；其余全部设置逐字段与失败演奏一致。

## 原因与修复

规划与动作验证已成功，失败发生于原生画面导出参数检查。源 AFF 的 `AudioOffset:-1297`，所以 `plan.preview.audio_start_ms=-1297`；它表示先有 **1297 ms** 静音，再开始歌曲。`Export.Start` 错误要求 `from >= 0`，因而返回 `Expected --export-aff-video OUTPUT START_MS END_MS FFMPEG.`。工作台原包装只截取 Unity 退出日志尾部，真正错误被内存统计埋掉，界面只显示通用失败。

原生 `FrameRenderer` 时间轴、`AudioRenderer.GetSongSamples` 及回放分轨均支持负音频起点。修复去掉错误的非负限制，仍要求整数与 `to > from`，不夹取起点、不改谱面或触点。导出失败包装提取原生原因、退出码与完整日志路径，避免以后误报为设置问题。

真实回放原本以 60 fps 生成，但 shell 又转为 30 fps。现在无声画面 stream copy 保留 60 fps，脚本源码参与缓存键使旧 30 fps 缓存失效。WebGL 录制增加独立 30／60 fps 选择（默认 60），不进入接触或动作设置。Blender 原离线入口仍按原 30 fps 时间轴工作。

## 验证

- 对修复后的实际 `Export.Start` 入口编译执行：负起点、零起点及正常正起点均接受；倒序、空区间和非整数拒绝。shell 假失败进程回归确认显示真正原因而非退出噪音。
- 原 175 项 Python 测试通过，另两项新原生 CLI 回归通过；Node 录制器覆盖 30／60 fps 选择、非法帧率、音频图复用、取消和状态恢复，翻译覆盖也通过。
- 完整重建从原保存 `run.settings` 提交，逐字段断言一致。规划 JSON 内容完全相同（仅序列化排版不同），动作和触点回放文件字节一致。原生文件 **1148×802、60/1 fps、161.466667 s**，含 AAC 音频。
- 原生结果：**1444 命中、0 漏键**；规划中的蛇物量 **549/549** 全部由原生回放确认。
- 实时录制使用同一 GLB、60 Hz 动作、原相机与 60 fps 游戏画面；初始对齐误差 **4.89e-9 m**，播放中约 **120 fps**、p95 帧间隔 **9.1 ms**（开发 Mac 数据）。

最终成片：`output/runs/20261107-052526-611446/arghena-0-160.797-60fps.mp4`，**856×642、60/1 fps、9693 帧、161.55 s、H.264／AAC、43,773,604 字节**。原 WebGL 录制平均约 **59.48 fps**，为前台捕获的轻微帧间隔波动；最终用 FFmpeg 规范为恒定 60 fps，音频流直接复制。没有把旧 30 fps 游戏素材插帧冒充原生 60 fps。

首／中／尾三段音轨与原生源相关为 **0.966／0.978／0.971**，共同采集延迟均为 **73.375 ms**，未观察到累计漂移。基于屏幕投影的画面匹配估计共同视觉延迟约 **50–67 ms**（一帧级分辨率），没有通过单独移动歌曲去抵消共同启动延迟，原歌曲延迟设置仍为 0。

已看实际 **0.8 s** 开头、**114.5 s** 交叉动作与 **160.5 s** 结束帧；整段 FFmpeg 解码无错误。Tailscale 成片范围请求返回 **HTTP 206**。证据位于 `output/60fps-qa/`（截图、真实帧、音画检查）及新演奏的 `export-60fps.json`。原始浏览器文件保留为 `preview-webgl-60fps-raw.mp4`。
